Why this table is required
The spec defines 25 sub-questions across 5 criteria (5 each) + 3 additional questions. The team's proposed model only has ReviewRating(score 1–5) with no way to store per-question answers or handle the mixed types (rating, text, boolean) of the Additional Questions section.

4. Design Gaps Found in the Spec

Gap 1 — No per-question granularity in ReviewRating
The spec explicitly states "each question's answer needs to be recorded separately" (25 sub-questions + 3 additional). The original model has ReviewRating(criterionId, score) which can only store one score per criterion, not per sub-question. EwayQuestion table is mandatory.
Gap 2 — No junction table for Cycle ↔ Criteria selection
The spec says admins "select active eWay criteria" per cycle. The ReviewCycle entity as specified has no FK list or join table for this. CycleCriteria join table is mandatory.
Gap 3 — Additional Questions not mapped to Review entity
The 3 additional questions (attention text, doing-well text, would-pick-for-team boolean) are not represented in the Review entity. They need either dedicated columns or to flow through ReviewRating via EwayQuestion. Recommendation: store attentionComment, wouldPickForTeam as columns on Review for simplicity; Additional Q2 ("doing well") maps to doWellComment.
Gap 4 — isMandatory flag missing from Nomination
The manager must be locked and cannot be removed. Without a isMandatory boolean on Nomination the UI has no DB-level signal to enforce this — it would be purely frontend logic, which is fragile.
Gap 5 — No draft status for the Nomination set (vs individual nominees)
A nomination row represents a single nominee. But the employee's entire nomination submission also has a state (DRAFT vs SUBMITTED). This is best handled with a nominationStatus column on the Nomination rows or a separate NominationSubmission header table.
Gap 6 — XLSX import columns need to map to schema
The employee XLSX has 8 columns (Key, First Name, Last Name, Job Title, Email, Department, Manager, Job Grade). Manager is stored as a full name string, not an ID. The import process must resolve manager names to Employee.id — this needs handling in the seeding logic. Also, employeeKey (HR system key) should be stored for idempotent re-imports.

5. Seed Data Requirements

Employee Seed (from XLSX)
  • 57 employees across 8+ departments
  • Columns: Key, First/Last Name, Email, Dept, Manager, Job Title, Job Grade
  • Manager resolved by full name match
  • Import order: Departments first → Employees (no manager) → Set managerId in second pass
  • Default role = EMPLOYEE; promote specific users to HR_ADMIN / LINE_MANAGER
eWay Criteria Seed
  • 5 criteria: MASTERFUL, EXCELLENCE, EXECUTION, COMMITMENT, CONTRIBUTION
  • 5 sub-questions each = 25 EwayQuestion rows
  • 3 additional questions (on a 6th "ADDITIONAL" criterion)
  • Answer types: RATING (Q1–25), TEXT (AQ1, AQ2), BOOLEAN (AQ3)
  • All seeded in a single migration / seed script
